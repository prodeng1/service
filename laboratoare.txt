Part 4: Git Workflow and Best Practices

Task 4.1: Understanding Trunk-Based Development

What is Trunk-Based Development?

Trunk-based development is a branching model where developers collaborate on code in a single branch called main (the trunk), using short-lived feature branches that are merged frequently.

Key Principles:

Small, frequent commits to the main branch
Short-lived feature branches (ideally 1-2 days max)
Continuous integration
Always keep main branch in a working state
Benefits:

Reduces merge conflicts
Encourages continuous integration
Faster feedback loops
Simplifies collaboration
Workflow Diagram:

main branch (trunk):  ●━━━━━●━━━━━●━━━━━●━━━━━●
                           ╱      ╱      ╱
feature branches:      ●━●    ●━●    ●━●
                      (short-lived)

Task 4.5: Keeping Your Branch Up to Date

Before creating a PR, always sync with main:

# Make sure you have latest changes from main
git fetch origin
git pull origin main:main

# Rebase your feature branch on top of main
git checkout feature/update-readme
git rebase main 
What does rebase do?

Rebase rewrites your branch's history to appear as if you created it from the current state of main. This creates a clean, linear history.

If conflicts occur:

# Git will pause and show conflicts
# Edit the conflicting files to resolve

# After resolving, stage the changes
git add <resolved-files>

# Continue the rebase
git rebase --continue

# If you want to abort
git rebase --abort

Task 4.4: Understanding MongoConfig.java

Open src/main/java/ro/unibuc/prodeng/config/MongoConfig.java

This class configures the MongoDB connection for Spring Boot:

@Configuration
public class MongoConfig extends AbstractMongoClientConfiguration {

   @Value("${mongodb.connection.url}")
   private String connectionURL;

   @Override
   protected String getDatabaseName() {
      return "test";
   }

   @Override
   public MongoClient mongoClient() {
      MongoClientSettings mongoClientSettings = MongoClientSettings.builder()
              .applyConnectionString(new ConnectionString(connectionURL))
              .build();

      return MongoClients.create(mongoClientSettings);
   }

   @Override
   public Collection<String> getMappingBasePackages() {
      return Collections.singleton("ro.unibuc.prodeng.model");
   }
}
Key points:

@Configuration - Marks this as a configuration class
@Value - Injects property values from application.properties
getMappingBasePackages - Classes under the provided package will be picked up as MongoDB collections (database entities)

Part 6: Understanding the Application Architecture

Task 6.1: Spring Boot Layers

Spring Boot applications typically follow a layered architecture:

┌─────────────────────────────────────┐
│         Controller Layer            │  ← HTTP Endpoints (REST API)
│  (UserController, TodoController)   │
└─────────────────────────────────────┘
           ↓ calls
┌─────────────────────────────────────┐
│          Service Layer              │  ← Business Logic
│  (UserService, TodoService)         │
└─────────────────────────────────────┘
           ↓ calls
┌─────────────────────────────────────┐
│        Repository Layer             │  ← Database Access
│  (UserRepository, TodoRepository)   │
└─────────────────────────────────────┘
           ↓ queries
┌─────────────────────────────────────┐
│      Database (such as MongoDB)     │  ← Data Storage
└─────────────────────────────────────┘
Layer responsibilities:

Controller Layer:

Handles HTTP requests
Validates input
Returns HTTP responses
NO business logic here!
Service Layer:

Contains business logic
Coordinates between multiple repositories
Handles transactions
Throws business exceptions
Repository Layer:

Direct database access
CRUD operations
Custom queries
Task 6.2: Data Flow Example

Let's trace a request through all layers:

Request: POST /api/users with body {"name": "John", "email": "john@example.com"}

1. Controller UserController receives request:

@PostMapping
public ResponseEntity<UserResponse> createUser(@RequestBody CreateUserRequest request) {
    // Validate input (Spring does basic validation)
    UserEntity user = userService.createUser(request);
    return ResponseEntity.ok(new UserResponse(user));
}
2. Service processes business logic:

    public UserResponse createUser(CreateUserRequest request) {
        if (userRepository.findByEmail(request.email()).isPresent()) {
            throw new IllegalArgumentException("Email already exists: " + request.email());
        }
        UserEntity user = new UserEntity(
                null, // ID will be generated by the repository
                request.name(),
                request.email()
        );
        UserEntity saved = userRepository.save(user);
        return toResponse(saved);
    }
3. Repository saves to database:

@Repository
public interface UserRepository extends MongoRepository<UserEntity, String> {

   Optional<UserEntity> findByEmail(String email);
}
4. MongoDB stores the document

5. Response flows back up:

Repository → Service → Controller → HTTP Response

Task 7.4: General error handling

Spring Boot provides a centralized way to handle exceptions across all controllers using @RestControllerAdvice. This ensures consistent error responses throughout your API.

Understanding GlobalExceptionHandler:

Open src/main/java/ro/unibuc/prodeng/exception/GlobalExceptionHandler.java

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, String>> handleIllegalArgument(IllegalArgumentException ex) {
        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(Map.of("error", ex.getMessage()));
    }

    @ExceptionHandler(EntityNotFoundException.class)
    public ResponseEntity<Map<String, String>> handleEntityNotFound(EntityNotFoundException ex) {
        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(Map.of("error", ex.getMessage()));
    }
}
How it works:

@RestControllerAdvice - Marks this class as a global exception handler for all REST controllers
@ExceptionHandler - Specifies which exception type this method handles
When any controller throws an exception, Spring automatically routes it to the appropriate handler
Exception handling examples:

IllegalArgumentException → 400 Bad Request

Used for invalid business logic (e.g., duplicate email, invalid ISBN)
Returns error message in JSON format: {"error": "Email already exists"}
EntityNotFoundException → 404 Not Found

Used when a requested resource doesn't exist (e.g., user ID not found)
Returns error message in JSON format: {"error": "User not found with id: 123"}
Example flow:

// In UserService.java
public UserResponse getUserById(String id) throws EntityNotFoundException {
   UserEntity user = userRepository.findById(id)
           .orElseThrow(() -> new EntityNotFoundException(id));
   return toResponse(user);
}
When a user with the given ID doesn't exist:

Service throws EntityNotFoundException
GlobalExceptionHandler catches it
Returns 404 Not Found with {"error": "User not found with id: 123"}

Part 1: Understanding Testing

Task 1.1: The Testing Pyramid

Software testing follows a pyramid structure:

Testing Pyramid

The Testing Pyramid consists of three layers:

Unit Tests (Base - Many): Test individual units in isolation. Fast, cheap, highest count.
Integration Tests (Middle - Some): Test multiple components together. Medium speed and cost.
E2E Tests (Top - Few): Test the entire system end-to-end. Slow, expensive, most realistic.
Today's focus: Unit Tests!

Task 1.2: What is Unit Testing?

Unit Testing means testing individual "units" of code in isolation.

A unit is:

A single method
A single class
A small, independent piece of functionality
Key characteristics:

Fast - Runs in milliseconds
Isolated - No external dependencies (DB, network, files)
Repeatable - Same result every time
Self-checking - Automatically verifies results
Focused - Tests one thing at a time
Example:

// This is a unit
public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }
}

// This is a unit test
class CalculatorTest {
    @Test
    void testAdd() {
        Calculator calc = new Calculator();
        int result = calc.add(2, 3);
        assertEquals(5, result);
    }
}
Task 1.3: Why Write Tests?

Benefits of testing:

Catch bugs early - Find issues before production
Enable refactoring - Change code with confidence
Documentation - Tests show how code should be used
Design feedback - Hard-to-test code is often poorly designed
Regression prevention - Ensure old bugs don't come back
Team confidence - Know your code works
Industry perspective: Most professional software development requires test coverage above a certain threshold, like 80%.

Task 3.2: Assertions

Assertions verify expected outcomes:

import static org.junit.jupiter.api.Assertions.*;

@Test
void demonstrateAssertions() {
    // Equality
    assertEquals(expected, actual);
    assertEquals(expected, actual, "Custom failure message");
    assertNotEquals(unexpected, actual);
    
    // Boolean conditions
    assertTrue(condition);
    assertFalse(condition);
    
    // Null checks
    assertNull(object);
    assertNotNull(object);
    
    // Object identity
    assertSame(expected, actual);  // Same reference
    assertNotSame(obj1, obj2);
    
    // Exceptions
    assertThrows(ExceptionType.class, () -> {
        // Code that should throw
    });
    
    Exception ex = assertThrows(IllegalArgumentException.class, () -> {
        service.doSomething();
    });
    assertEquals("Expected message", ex.getMessage());
    
    // Collection assertions
    assertIterableEquals(expectedList, actualList);
    assertArrayEquals(expectedArray, actualArray);
    
    // Multiple assertions
    assertAll(
        () -> assertEquals(expected1, actual1),
        () -> assertEquals(expected2, actual2),
        () -> assertTrue(condition)
    );
}

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.springframework.test.context.junit.jupiter.SpringExtension;

import ro.unibuc.prodeng.model.TodoEntity;
import ro.unibuc.prodeng.model.UserEntity;
import ro.unibuc.prodeng.repository.TodoRepository;
import ro.unibuc.prodeng.request.CreateTodoRequest;
import ro.unibuc.prodeng.response.TodoResponse;
import ro.unibuc.prodeng.exception.EntityNotFoundException;

import java.util.Arrays;
import java.util.List;
import java.util.Optional;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.ArgumentMatchers.anyString;
import static org.mockito.Mockito.*;

@ExtendWith(SpringExtension.class)
class TodoServiceTest {

   @Mock
   private TodoRepository todoRepository;

   @Mock
   private UserService userService;

   @InjectMocks
   private TodoService todoService;

   @Test
   void testGetTodoById_existingTodoRequested_returnsTodo() throws EntityNotFoundException {
      // Arrange
      UserEntity user = new UserEntity("1", "Alice", "alice@example.com");
      TodoEntity todo = new TodoEntity("todo-1", "Complete project", false, "1");

      when(todoRepository.findById("todo-1")).thenReturn(Optional.of(todo));
      when(userService.getUserEntityById("1")).thenReturn(user);

      // Act
      TodoResponse result = todoService.getTodoById("todo-1");

      // Assert
      assertNotNull(result);
      assertEquals("todo-1", result.id());
      assertEquals("Complete project", result.description());
      assertFalse(result.done());
      assertEquals("Alice", result.assigneeName());
      assertEquals("alice@example.com", result.assigneeEmail());
   }

   @Test
   void testGetTodoById_nonExistingTodoRequested_throwsEntityNotFoundException() {
      // Arrange
      when(todoRepository.findById("non-existing")).thenReturn(Optional.empty());

      // Act & Assert
      assertThrows(EntityNotFoundException.class, () -> todoService.getTodoById("non-existing"));
   }
}

Part 4: Mocking with Mockito

Task 4.1: Why Mocking?

Problem: Unit tests should be isolated, but services depend on repositories, and repositories need databases.

Solution: Mocking - Creating fake objects that simulate real behavior.

Real flow:
Service → Repository → Database
  ↓          ↓          ↓
Slow      Slow       Slow

Mocked flow:
Service → Mock Repository (in memory)
  ↓          ↓
Fast      Fast

Task 4.3: Stubbing (Defining Behavior)

Stubbing tells mocks what to return:

import static org.mockito.Mockito.*;

// Return a value
when(mockRepo.findById("123"))
    .thenReturn(Optional.of(user));

// Return different values on successive calls
when(mockRepo.count())
    .thenReturn(5L)
    .thenReturn(6L);

// Throw an exception
when(mockRepo.findById("invalid"))
    .thenThrow(new IllegalArgumentException("Invalid ID"));

// Return based on any argument
when(mockRepo.findById(anyString()))
    .thenReturn(Optional.of(user));

// Return based on argument matcher
when(mockRepo.findByEmail(startsWith("admin")))
    .thenReturn(Optional.of(adminUser));

// Do nothing (for void methods)
doNothing().when(mockRepo).deleteById(anyString());

// Custom logic with Answer
when(mockRepo.save(any(UserEntity.class)))
    .thenAnswer(invocation -> {
        UserEntity user = invocation.getArgument(0);
        user.setId("generated-id");
        return user;
    });
Task 4.4: Verification

Verification ensures methods were called correctly:

// Verify method was called with expected parameters
verify(mockRepo).findById("123");

// Verify call count
verify(mockRepo, times(2)).findAll();
verify(mockRepo, atLeastOnce()).save(any());
verify(mockRepo, atMost(3)).findById(anyString());
verify(mockRepo, never()).deleteById(anyString());

// Verify with argument matchers
verify(mockRepo).save(argThat(user -> 
    user.getEmail().contains("@example.com")
));

// Verify order of calls
InOrder inOrder = inOrder(mockRepo);
inOrder.verify(mockRepo).findById("123");
inOrder.verify(mockRepo).save(any());

// Verify no more interactions
verify(mockRepo).findById("123");
verifyNoMoreInteractions(mockRepo);

Task 7.3: Test Coverage with JaCoCo

JaCoCo is a code coverage library that integrates with Gradle to measure what percentage of your code is covered by tests.

Generally, the higher code coverage is, the more safe the code is considered, due to being secured by tests.

Note JaCoCo plugin in build.gradle:

test {

		excludeTags ("IntegrationTest", "E2E")

	finalizedBy jacocoTestReport

jacoco {
	toolVersion = "0.8.9"
}

jacocoTestReport {
	dependsOn test
	reports {
		xml.required = true
		html.required = true
	}
	afterEvaluate {
		classDirectories.setFrom(files(classDirectories.files.collect {
			fileTree(dir: it, exclude: [
				'**/config/**',
				'**/exception/**',
				'**/model/**',
				'**/repository/**',
				'**/request/**',
				'**/response/**',

The task jacocoTestReport is configured to generate coverage reports both in HTML format (human readable) and XML format, which can be more easily interpreted by automated checks (CI/CD).

These packages are considered to either not be testable or not bring value in unit testing, since when tested by themselves in isolation, without interacting with other components (as opposed to integration testing - lab 5), these classes do not contain much logic to test.

Unit test coverage should concentrate on pieces of code where unit tests bring value (such as services, controllers).

Task 8.1: Test Naming Conventions

Use descriptive names that explain the test:

Pattern:

Task 8.2: AAA Pattern (Arrange-Act-Assert)

Structure every test with AAA:

@Test
void testExample() {
    // ARRANGE - Set up test data and expectations
    UserEntity user = new UserEntity();
    user.setId("123");
    when(repository.findById("123")).thenReturn(Optional.of(user));
    
    // ACT - Execute the method being tested
    UserEntity result = service.getUserById("123");
    
    // ASSERT - Verify the results
    assertNotNull(result);
    assertEquals("123", result.getId());
    verify(repository).findById("123");
}

Task 2.2: Integration Test Base Class

Using a base class for integration tests allows us to set up and tear down the MongoDB container only once for all tests, and to configure Spring Boot to connect to it.

A main advantage of this class would be that we only need to define shared logic of all tests, such as database connections, in a single location. It will then be reusable by all inheriting tests.

Note src/test/java/ro/unibuc/prodeng/IntegrationTestBase.java:

package ro.unibuc.prodeng;

import org.junit.jupiter.api.Tag;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.MongoDBContainer;
import org.testcontainers.junit.jupiter.Testcontainers;

/**
 * Base class for integration tests that need a real MongoDB database.
 * Uses Testcontainers to spin up a MongoDB instance in Docker.
 */
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureMockMvc
@Testcontainers
@Tag("IntegrationTest")
public abstract class IntegrationTestBase {
   private static final MongoDBContainer mongoDBContainer =
           new MongoDBContainer("mongo:6.0.20")
                   .withExposedPorts(27017)
                   .withSharding()
                   .withLabel("ro.unibuc.prodeng", "integration-test-mongo");

   static {
      mongoDBContainer.start();
   }

   @DynamicPropertySource
   static void setProperties(DynamicPropertyRegistry registry) {
      String mongoUrl = "mongodb://localhost:" + mongoDBContainer.getMappedPort(27017);
      registry.add("mongodb.connection.url", () -> mongoUrl);
   }
}
What this does:

Starts a real MongoDB container before tests
Configures Spring Boot to connect to test container
Provides common setup for all integration tests
Stops container after all tests complete

Task 4.1: Understanding BDD and Gherkin

BDD (Behavior-Driven Development) describes system behavior in plain language that non-technical stakeholders can understand.

Gherkin is the language used to write BDD scenarios.

Key concepts:

Feature: High-level functionality
  Describes what the feature does

Scenario: Specific test case
  Given [initial context]
  When [action occurs]
  Then [expected outcome]
  And [additional conditions]
Example:

Feature: User Management
  As a system administrator
  I want to manage users
  So that I can control access to the system

Scenario: Create a new user
  Given I have user creation credentials
  When I create a user with name "John Doe" and email "john@example.com"
  Then the user should be saved in the system
  And I should receive a success response

Part 5: Performance Testing

JMeter is a powerful tool for load testing and performance measurement. It allows you to simulate multiple users sending requests to an application and analyze how your service performs under load.

Through JMeter, tests are defined as a series of requests (samplers) that can be configured to run concurrently (thread groups) and with various parameters (timers, assertions). JMeter provides real-time results and detailed reports to help identify performance bottlenecks.

Tests in JMeter are defined via an user interface which does not require coding knowledge, then saved as XML files. Other performance testing tools use different approaches for writing tests (such as Gatling, where performance tests are written as Java code).

You can use any tool you are familiar with or you find more intuitive.

Part 1: Understanding Continuous Integration

Task 1.1: What is Continuous Integration?

Continuous Integration (CI) is a development practice where team members integrate their code changes into a shared repository frequently — ideally several times a day. Each integration is verified by an automated build and test process to detect problems early.

Without CI:

Developer A pushes code on Monday
Developer B pushes code on Friday
Merge conflicts, broken builds, and integration bugs discovered late
Hours spent debugging integration issues
With CI:

Developer A pushes code → CI builds & tests → ✅ Passes → Merged
Developer B pushes code → CI builds & tests → ❌ Fails → Fix immediately
Problems caught within minutes, not days
Key Principles:

Maintain a single source repository — all code lives in one place (your GitHub repo)
Automate the build — no manual steps to compile and package
Make the build self-testing — unit and integration tests run automatically
Everyone commits frequently — small, frequent changes reduce risk
Every commit triggers a build — immediate feedback on every change
Fix broken builds immediately — a broken build is the team's top priority
Keep the build fast — feedback should come in minutes, not hours
Benefits of CI:

Benefit	Without CI	With CI
Bug detection	Found days/weeks later	Found in minutes
Integration issues	Painful merge conflicts	Small, manageable merges
Build reliability	"Works on my machine"	Consistent, reproducible builds
Team confidence	Afraid to merge	Merge with confidence
Release readiness	Weeks of stabilization	Always deployable
Task 1.2: CI Pipeline Stages

A typical CI pipeline follows these stages:

┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  Source  │───>│  Build   │───>│   Test   │───>│ Package  │───>│ Publish  │
│  (Git)   │    │(Compile) │    │  (Unit)  │    │ (Docker) │    │(Registry)│
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
Source — Developer pushes code to Git. CI server detects the change.
Build — The project is compiled. Dependencies are resolved.
Test — Unit tests run. If any test fails, the pipeline stops.
Package — The application is packaged into a deployable artifact (Docker image).
Publish — The Docker image is pushed to a registry (Docker Hub).
Task 1.3: What is Jenkins?

Jenkins is the most widely-used open-source automation server. It provides hundreds of plugins to support building, deploying, and automating any project.

Key concepts:

Concept	Description
Job	A task Jenkins executes (build, test, deploy). Also called a "project".
Build	A single execution of a job. Each build has a number and a result (success/failure).
Pipeline	A series of stages defined in code (Jenkinsfile).
Freestyle Project	A simple, UI-configured job. Good for getting started.
Pipeline Project	A code-defined job using a Jenkinsfile. Better for complex workflows.
Workspace	The directory where Jenkins checks out code and runs builds.
Plugin	An extension that adds functionality (Git, Docker, Gradle, etc.).
Freestyle vs Pipeline:

Aspect	Freestyle Project	Pipeline (Jenkinsfile)
Configuration	Through Jenkins web UI	Written as code in repository
Version control	Not version controlled	Version controlled with your code
Complexity	Simple, limited	Supports complex workflows
Reusability	Must be recreated manually	Portable across Jenkins instances
Code review	Not possible	Can be reviewed in PRs
Best for	Quick prototyping, simple builds	Production CI/CD pipelines

Part 2: Jenkins Setup

Task 2.1: Understanding the Jenkins Container

Jenkins is already configured in your project's docker-compose.yml. Let's understand the configuration:

jenkins:
  image: jenkins/jenkins
  ports:
    - 8082:8080       # Jenkins web UI
    - 50000:50000     # Agent communication port
  restart: on-failure
  volumes:
    - type: bind
      source: ${JENKINS_CONFIG_ROOT:-/workspaces/jenkins_config}
      target: /var/jenkins_home                                    # Persist Jenkins data
    - /var/run/docker.sock:/var/run/docker.sock         # Allow Jenkins to use host Docker
    - /usr/bin/docker:/usr/bin/docker                   # Docker CLI binary
    - ./Dockerfile:/Dockerfile                          # Access to Dockerfile
    - /usr/libexec/docker/cli-plugins/docker-compose:/usr/libexec/docker/cli-plugins/docker-compose
  profiles:
    - "prod-eng-service"
  user: 0:0           # Run as root (needed for Docker socket access)
Key volume mounts explained:

**jenkins_config:/var/jenkins_home** — Persists Jenkins configuration, jobs, and plugins between container restarts. Without this, you'd lose everything when the container stops. The path defaults to /workspaces/jenkins_config (for Codespaces) and can be overridden via the JENKINS_CONFIG_ROOT environment variable.
**/var/run/docker.sock** — The Docker socket. This allows Jenkins (running inside a container) to communicate with the host's Docker daemon and build/run Docker images. This is called "Docker-in-Docker" (DinD) via socket mounting.
**/usr/bin/docker** — Makes the Docker CLI available inside the Jenkins container.
**./Dockerfile:/Dockerfile** — Makes your application's Dockerfile accessible to Jenkins for building images.
Task 2.2: Starting Jenkins

Before starting Jenkins, you need a local Docker image for your service:

./build.sh
./start.sh
Running locally (outside Codespaces): The default Jenkins home path (/workspaces/jenkins_config) only exists in Codespaces. When running on your own machine, pass the JENKINS_CONFIG_ROOT variable so Jenkins data is stored in your project directory:

./build.sh
mkdir -p jenkins_config
JENKINS_CONFIG_ROOT=$(pwd)/jenkins_config ./start.sh
Apple Silicon (M1/M2/M3) Macs — Docker inside Jenkins: The docker-compose.yml bind-mounts /usr/bin/docker and the Docker Compose plugin from the host. These are macOS (darwin) binaries and cannot run inside the Linux-based Jenkins container, so Docker commands in Jenkins jobs will fail with "Permission denied".

After starting Jenkins, install a native Docker CLI inside the container:

docker exec service-jenkins-1 bash -c "curl -fsSL https://download.docker.com/linux/static/stable/\$(uname -m)/docker-27.5.1.tgz | tar xz --strip-components=1 -C /usr/local/bin docker/docker"
This downloads a native Linux Docker binary to /usr/local/bin/docker, which takes precedence in PATH over the broken macOS binary mounted at /usr/bin/docker. You need to re-run this command if you recreate the container (docker compose down + up), but not after a simple restart.
Verify Jenkins is running:

docker ps | grep jenkins
You should see a container with the Jenkins image mapping port 8082 to 8080.

Task 4.1: Understanding Semantic Versioning

Before we build Docker images, we need a versioning strategy. Semantic Versioning (SemVer) is the industry standard format: MAJOR.MINOR.PATCH.

    1.2.3
    │ │ │
    │ │ └── PATCH: Bug fixes, backwards compatible
    │ └──── MINOR: New features, backwards compatible
    └────── MAJOR: Breaking changes
When to increment each number:

Version Change	When	Example
MAJOR (1.0.0 → 2.0.0)	Breaking API changes	Removing an endpoint, changing request format
MINOR (1.0.0 → 1.1.0)	New features, backwards compatible	Adding a new endpoint
PATCH (1.0.0 → 1.0.1)	Bug fixes, backwards compatible	Fixing a null pointer exception
Real-world examples:

1.0.0 → Initial release
1.1.0 → Added search functionality
1.1.1 → Fixed search returning duplicates
2.0.0 → Redesigned API (breaking change)

Task 4.3: Automated Version Bumping in Jenkins

Now let's configure Jenkins to automatically determine the next version and build a Docker image with that tag.

Go to your build-application job → "Configure" → "Build Steps" → "Add build step" → "Execute shell":

# Fetch all tags from remote
git fetch --tags

# Extract version components from the latest tag
# sort -V sorts by version number (1.2.0 < 1.10.0)
# tail -1 gets the last (highest) version
export MAJOR_VERSION=$(git tag | sort -V | tail -1 | cut -d . -f 1)
export MINOR_VERSION=$(git tag | sort -V | tail -1 | cut -d . -f 2)
export PATCH_VERSION=$(git tag | sort -V | tail -1 | cut -d . -f 3)

# Increment the minor version for the new build
export NEW_MINOR_VERSION=$((MINOR_VERSION + 1))

# Construct the new image version string
export IMAGE_VERSION=$MAJOR_VERSION.$NEW_MINOR_VERSION.$PATCH_VERSION

echo "Current tag: $MAJOR_VERSION.$MINOR_VERSION.$PATCH_VERSION"
echo "Building image version: $IMAGE_VERSION"

# Build a Docker image with the new version tag
docker build -t prod-eng-img:$IMAGE_VERSION -f /Dockerfile .
Line-by-line explanation:

Line	Purpose
git fetch --tags	Ensures Jenkins has all tags from the remote repository
`git tag	sort -V
cut -d . -f 1	Extracts the first field using . as delimiter (MAJOR)
cut -d . -f 2	Extracts the second field (MINOR)
cut -d . -f 3	Extracts the third field (PATCH)
$((MINOR_VERSION + 1))	Bash arithmetic to increment the minor version
docker build -t ... -f /Dockerfile .	Builds a Docker image with the version tag
Run the Jenkins job again. It should finish with SUCCESS and produce a tagged Docker image.

Part 6: Pipeline as Code with Jenkinsfile

Task 6.1: Why Pipeline as Code?

So far, you've configured your Jenkins job through the web UI. This has several drawbacks:

Not version controlled — if someone changes the job configuration, there's no history
Not reviewable — team members can't review changes via pull requests
Not portable — recreating the job on another Jenkins instance requires manual work
Not scalable — complex pipelines become unwieldy in the UI
Pipeline as Code solves these problems by defining your entire CI pipeline in a Jenkinsfile — a text file committed to your repository alongside your source code.

Benefits:

Benefit	Description
Version controlled	Pipeline changes are tracked in Git history
Code reviewable	Pipeline changes go through the same PR process as code
Portable	Move to a new Jenkins instance by simply scanning your repo
Self-documenting	Anyone can read the Jenkinsfile to understand the CI process
Branch-specific	Different branches can have different pipelines
Task 6.2: Store Credentials Securely

Before writing the Jenkinsfile, let's store sensitive credentials properly in Jenkins instead of hardcoding them.

Go to "Manage Jenkins" → "Credentials" → "(global)" → "Add Credentials":

1. Docker Hub credentials:

Field	Value
Kind	Username with password
Username	Your Docker Hub username
Password	Your Docker Hub password
ID	docker_password
Description	Docker Hub credentials
2. GitHub Personal Access Token:

First, generate a token:

Go to GitHub Settings → Developer settings → Personal Access Tokens → Tokens (classic)
Click "Generate new token (classic)"
Select scopes: repo (full control of private repositories)
Copy the generated token
Then add it to Jenkins:

Field	Value
Kind	Username with password
Username	Your GitHub username
Password	Your GitHub token
ID	github_token
Description	GitHub Personal Access Token
Why "Username with password" instead of "Secret text"? The GitHub Organization Folder plugin requires credentials of type "Username with password" to authenticate with the GitHub API when scanning for repositories. If you store the token as "Secret text", the Organization Folder configuration won't be able to select it in the credentials dropdown.
Task 6.3: Understanding the Jenkinsfile

The project includes a starter Jenkinsfile at infrastructure/Jenkinsfile. Let's expand it into a complete CI pipeline.

Update the file with the following content:

pipeline {
    agent any

    tools {
        jdk 'jdk21'
        gradle 'gradle-8'
    }

    environment {
        DOCKER_HUB_USERNAME = 'YOUR_DOCKERHUB_USERNAME'
        DOCKER_PASSWORD = credentials('docker_password')
        GITHUB_TOKEN = credentials('github_token')
    }

    stages {
        stage('Build') {
            steps {
                sh './gradlew clean build'
            }
        }

        stage('Test') {
            steps {
                sh './gradlew test'
            }
        }

        stage('Version & Tag') {
            steps {
                script {
                    sh 'git fetch --tag'
                    env.MAJOR_VERSION = sh(
                        script: 'git tag | sort -V | tail -1 | cut -d . -f 1',
                        returnStdout: true
                    ).trim()
                    env.MINOR_VERSION = sh(
                        script: 'git tag | sort -V | tail -1 | cut -d . -f 2',
                        returnStdout: true
                    ).trim()
                    env.PATCH_VERSION = sh(
                        script: 'git tag | sort -V | tail -1 | cut -d . -f 3',
                        returnStdout: true
                    ).trim()
                    def minorInt = env.MINOR_VERSION.toInteger()
                    env.IMAGE_TAG = "${env.MAJOR_VERSION}.${minorInt + 1}.${env.PATCH_VERSION}"
                    echo "Building version: ${env.IMAGE_TAG}"
                }
            }
        }

        stage('Build Docker Image') {
            steps {
                sh 'docker build -t $DOCKER_HUB_USERNAME/prod-eng-img:$IMAGE_TAG .'
            }
        }

        stage('Push to Docker Hub') {
            steps {
                sh '''
                    echo $DOCKER_PASSWORD_PSW | docker login -u $DOCKER_HUB_USERNAME --password-stdin
                    docker push $DOCKER_HUB_USERNAME/prod-eng-img:$IMAGE_TAG
                '''
            }
        }

        stage('Tag Release') {
            steps {
                sh '''
                    git tag $IMAGE_TAG
                    git push https://$GITHUB_TOKEN_PSW@github.com/YOUR-ORG/service.git $IMAGE_TAG
                '''
            }
        }
    }

    post {
        always {
            sh 'docker logout'
        }
    }
}
Replace YOUR_DOCKERHUB_USERNAME and YOUR-ORG/service.git with your actual values.

Let's break down each section:

Jenkinsfile Section-by-Section Explanation (Click to expand)

**pipeline { agent any }**

pipeline — Defines this as a Declarative Pipeline (as opposed to Scripted Pipeline)
agent any — Run the pipeline on any available Jenkins agent/executor
**tools { ... }**

Tells Jenkins which pre-configured tools this pipeline needs
Jenkins will install them if not already available
Names must match what you configured in "Manage Jenkins" → "Tools"
**environment { ... }**

Defines environment variables available to all stages
credentials('docker_password') — Securely retrieves the credential you stored earlier
credentials('github_token') — For "Username with password" credentials, Jenkins automatically creates three variables: GITHUB_TOKEN (as username:password), GITHUB_TOKEN_USR (username), and GITHUB_TOKEN_PSW (password/token). We use GITHUB_TOKEN_PSW in the git push URL.
The credential values are masked in console output (shown as ****)
**stage('Build') and stage('Test')**

sh './gradlew clean build' — Runs Gradle to compile and package
sh './gradlew test' — Runs unit tests
If any stage fails, the pipeline stops and is marked as FAILED
**stage('Version & Tag')**

Uses script { } block for more complex Groovy logic
returnStdout: true — Captures shell command output into a Groovy variable
.trim() — Removes whitespace/newlines from captured output
.toInteger() — Converts string to integer for arithmetic
**stage('Build Docker Image')**

Builds a Docker image using the version tag calculated in the previous stage
$DOCKER_HUB_USERNAME/prod-eng-img:$IMAGE_TAG — Image name format: username/repository:tag
Uses single quotes so shell variables are expanded by the shell, not Groovy
**stage('Push to Docker Hub')**

Uses single quotes (''') to avoid Groovy string interpolation of secrets (Jenkins warns about this as a security risk with double quotes)
$DOCKER_PASSWORD_PSW — The password portion of the "Username with password" credential (not $DOCKER_PASSWORD, which contains username:password)
--password-stdin — More secure than -p flag (doesn't show password in process list)
docker push — Uploads the image to Docker Hub
**stage('Tag Release')**

Creates a new Git tag with the version number
$GITHUB_TOKEN_PSW — The token portion of the "Username with password" credential
Pushes the tag to GitHub using the personal access token for authentication
This means every successful build creates a corresponding Git tag
**post { always { ... } }**

post — Actions to run after the pipeline completes
always — Runs regardless of whether the pipeline succeeded or failed
docker logout — Cleans up Docker Hub authentication

Task 6.5: Create Organization Folder

An Organization Folder is a Jenkins feature that automatically discovers repositories and branches that contain a Jenkinsfile. Instead of manually creating a job for each repository, Jenkins scans your GitHub organization and creates jobs automatically.

Why use Organization Folders?

Automatic discovery of new repositories and branches
No manual job creation needed
Jenkinsfile changes are picked up automatically
Clean organization of jobs by repository and branch
Steps:

Go to Jenkins Dashboard → "New Item"
Enter your GitHub organization name, select "Organization Folder", click "OK"
Under "Projects" → Select "GitHub Organization"
Configure:
Owner: Your GitHub organization name
Credentials: Select the github_token credential you created earlier
Under "Project Recognizers" → "Script Path":
Set to infrastructure/Jenkinsfile (this is where your Jenkinsfile lives)
Click "Save"
Filtering (if needed):

If the organization has multiple repositories and you only want to scan your service repo:

Under "Behaviours" → Click "Add" → "Filter by name (with regular expression)"
In the repository filter regex: .*service (matches only repos containing "service")
Click "Scan Organization Now" and verify:

Your repository is discovered
The jenkins branch is found
A pipeline job is created and starts running
Exercise:

Watch the pipeline execute in the Jenkins Blue Ocean view (if available) or the classic pipeline view
Click on each stage to see its console output
Verify the Docker image appears on Docker Hub with the correct version tag

Troubleshooting: Organization Folder Issues (Click to expand)

"API rate limit exceeded" error: GitHub limits unauthenticated API calls. Ensure you added the github_token credential to the Organization Folder configuration, not just globally.

Repository not discovered:

Check the owner name matches your GitHub organization exactly (case-sensitive)
Verify the token has repo scope
Check the "Filter by name" regex isn't too restrictive
Jenkinsfile not found:

Verify the "Script Path" is set to infrastructure/Jenkinsfile
Ensure the Jenkinsfile is pushed to the jenkins branch
Pipeline fails at Docker stage:

Verify Docker socket is mounted in docker-compose.yml
Check Docker permissions: docker exec -it service-jenkins-1 docker ps
